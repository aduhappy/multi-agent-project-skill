# 经验教训（规则背后的实测案例）

> 由 `AGENTS.md` §5 引出。**规则在 §5，理由在这里。**
> 每条都是真实撞出来的，不是设想。

## 1. 被动标记挡不住已经进来的 agent

往废弃的树里放「勿用」说明文件 —— 结果：
- 执行方**读到了、还在报告里引用了**，然后**照样在那棵树里干了一整轮**；
- 后来又有工具（写入审批被拒后回退）**在挂着标记的树里写入了文件**。

→ **拦截必须在「开跑第一条动作」，不能靠事后说明。** 标记只用于导航与审计。

## 2. 两个 API 对同一个名词给出相反答案

判断一个目录是不是 reparse point：
```
Get-Item  → Attributes 不含 0x400，报「不是」
fsutil    → Reparse Tag Value 0x9000e01a，报「是」
```
同一时刻、同一目录、结论相反（Cloud Files API 故意不设传统属性位）。
更麻烦的是**该属性随 hydration 状态在几十秒内翻转**。

→ **两源分歧首先说明「被测量量或语义没钉住」，不是「哪个工具对」。**
找第三个工具来投票**不解决问题**——所以**不照搬工业界的 2oo3 表决**：
那适用于被测量量无歧义的传感器冗余。分歧时记 `UNKNOWN`、钉语义。

## 3. 退出码相同，产物是错的

三份产物 rc 全绿、数据文件逐字节相同，**只有最终 HTML 不同** ——
差异是 gzip 头里的写盘时间戳。只比 rc 就放行了。

→ **除 rc 外必须对照产物哈希与汇总行。**

## 4. 「全树字面量归零」是个达不到的判据

某次迁移要求「全树扫旧路径，命中归 0」——
历史报告、归档、只读参考副本、打包产物里的脚本副本**永远会命中**，
实测残留数千处。执行方正确打回。

→ 判据必须限定在**活动执行面**（算出来的闭集），而不是全树。

## 5. 复核方错得比执行方多

某轮长链路里，**出卡方/复核方被证伪 15 次以上**，其中数次是
**用单一来源的错误测量去推翻执行方的正确判断**，还据此指责对方。

→ **复核方的结论同样要可证伪；执行方有权停下来质疑任务卡，质疑不计为失败。**

## 6. 同一段话写在两处，同一次提交里就漂移了

为了让规则「随卡走」，把同一段话术复制进了模板与文档共三处 ——
**同一次提交里就漏同步了一处，还在另一处留下自相矛盾的旧句**。

→ **全文只在一处，其余只写指针。** 但指针必须指向**有内容**的地方：
曾把修正版放进给「搭骨架的 agent」看的文件，而没同步落进项目的那份模板，
结果**实际生效的规则仍是旧的**。
