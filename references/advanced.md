# 进阶板块（项目变大时按需启用）

> 核心板块之外的可选增强。**不要一上来全堆**——小项目用不上，反而让入口变臃肿。
> 启用时，在 `AGENTS.md` §6 深读指针里放一行指针即可，主体内容下沉到本文件对应的文档。

## 1. 决策记录：先有"登记表"，再有"详卡"

决策记录解决一件事：**防止下个 agent 重新踩坑、重新质疑已定的事，或抄到一个早被推翻的口径。** 但自由式 ADR 散在文件夹里、或埋在 STATUS 长叙事里，**不可查、不可数**——长日志没人读全（接力事故的高发区）。所以分两层：

### 1a. 决策登记表（有界、可 grep —— 强烈推荐，优先于详卡）

一张表收口所有**具约束力**的决策，**一行一决策**，放 `AGENTS.md` 紧邻 §3 处（§3.5，唯一权威源）：

```markdown
## 3.5 决策登记表（具约束力的决策，单一权威源）
| ID | 状态 | 决策 | 取值/口径 | 理由 | 日期 | 证据文档 | 取代了谁 | 被谁取代 |
|----|------|------|-----------|------|------|----------|----------|----------|
| D-03 | ACTIVE | fPOC 拟合排除 H28 | H28 非年龄序列（3 树种横向比较） | 物种效应≠年龄效应 | 2026-06-25 | ->文档/H28复核.md | D-01 | -- |
| D-04 | ACTIVE | 退耕成熟值只报区间 | 0.45–0.55，不给单值 | >40yr 零实测 | 2026-06-27 | ->E8 决策卡 | -- | -- |
```

为什么是这张表、不是文件夹散卡：
- **有界**——一决策一行，永远读得完，符合"必读层"要求（硬要求 5）。
- **可查**——`grep H28 AGENTS.md` 秒命中权威行，不用扫长 STATUS、也不用猜哪个脚本对。
- **可追**——双向 supersession 链：旧行标 `SUPERSEDED` 且 `被谁取代` 填新 ID；新行 `取代了谁` 指回旧 ID。任何 agent 读到旧行都能顺着找到当前有效版本，不能静默覆盖。

> **判据**：任何约束后续工作的决策都登记在此表；建模/取数/复现前**先 grep 这张表**，别先信某个脚本的硬编码。表超过检查器 A003 体积线时，全文原样迁到 `文档/决策记录/决策登记表_全文.md`，§3.5 改为短行索引。

### 1b. 决策详卡 ADR（登记表某行需要展开时才写）

`文档/决策记录/<日期>_<主题>.md`，登记表里复杂的那几条再展开：
```markdown
# 决策：<一句话结论>
- 日期：YYYY-MM-DD
- 状态：采纳 / 已废弃 / 待定
- 背景：<遇到了什么问题>
- 选项：A... / B... / C...
- 决定：选 A
- 理由：<为什么，关键证据 / 谁拍板>
- 影响：<要改哪些代码 / 数据 / 流程>
```

### 1c. 口径参数 = 代码的单一来源（防多脚本编码漂移）

登记表治"决策写在哪"，这条治"代码怎么不跑偏"。**口径参数 / 样本集 / 排除清单不准在多个脚本里各自硬编码**——抽进唯一 config，所有脚本读它：

```python
# config/参数.py（或 .yaml）——唯一权威，对应决策登记表
AFF_STUDIES = {"4", "36", "H27"}          # 纳入拟合（D-02）
DROP_STUDIES = {"C6", "H28", "H15"}        # 排除（D-03，附理由见登记表）
```
```python
# 任何脚本里
from config.参数 import AFF_STUDIES, DROP_STUDIES   # 读，不复述
```

> 💡 **一条真实接力教训（硬要求 5/6/7 就是这么来的）**：某 agent 要重拟一条曲线，从一个**滞后脚本**里抄了样本集——那脚本还保留着早该剔除的坏点，而"剔除该点"的决策只躺在 600 行 STATUS 的深处，且两个脚本对它的编码恰好相反。结果该点把 R² 从 0.5 拖到 0.27，对外汇报被推翻。事后看，三处都本可拦住：决策没上浮到有界必读层（硬要求 5）、口径集合在多脚本里各自硬编码而非单一 config（硬要求 6）、被取代的旧脚本没打退役标记（硬要求 7）。**信滞后脚本、不信决策记录**是这类事故的共同根因。

### 1d. 被取代的脚本要退役（不只数据产物）

某决策一旦改了方法，**被它取代的旧脚本同样退役**：脚本顶部加注释，别让它当活口径把下家钓进去。
```python
# _DEPRECATED 2026-06-27 → 口径已改，见决策登记表 D-03 / 用 e5k3_*.py
```

## 2. 词汇表 / 缩写表
项目特有术语容易让新 agent 困惑。放 `文档/词汇表.md`：
```markdown
- <术语A> = <全称/定义>
- <缩写B> = <含义，尤其和通用义不同的项目特有口径>
- <易混淆对> = ...（如：X vs Y 的口径差异在哪里）
```
入口 §6 放指针，改文案时按表全查。

## 3. 进度日志（带日期戳的变更流水）
比 `AGENTS.md` §3"现在在哪"更细。放 `进度日志.md`，**最新在上**：
```markdown
## YYYY-MM-DD
- 完成数据集 X 的下载清洗（N 条），落在 <路径>
- 发现数据问题 N 行，T2 须标记
- 方向/口径定案（决策来源：<谁/哪次会>）
```
§3 只保留"最新 1–5 条 + 指针 → 完整流水看 `进度日志.md`"。

## 4. 验收具体化（Definition of Done）
任务卡的"验收/闸门"字段**不要写"完成就行"**，要写成可运行检查，且重开最终交付物本身核对：
- `python scripts/check_<quality>.py` → 输出某一致性指标全 < 阈值
- 文档/演示稿：重开落盘后的 `.docx` / `.pptx`，用脚本核页数、关键文字、图片数、字体
- 图：X/Y 轴有中文标题、无缺字方框、分辨率 ≥ 300 dpi
- CSV：列名、行数、单位符合 schema

判据：换个 agent 跑同样检查能复现"通过/不通过"。

## 5. 标准 handoff 摘要 + STATUS.md（增量交接落盘文件）

agent 收工时（执行方、复核方另回写任务卡“进度回写”，主控另更新 `AGENTS.md`）追加 **`STATUS.md`**（放在项目根目录）。这是下个 agent 的第一眼——**读这个就能接上当前工作，不依赖对话历史**。

**关键：STATUS.md 记增量，AGENTS.md §3 记累计快照，两者不重复。**
- `STATUS.md` = 固定四节（改了什么 / 怎么验证的 / 没做什么 / 不确定处）+ 谁做的，每段 ≤800 字（检查器 A011 提示）。
- `AGENTS.md` §3 = "现在整体到哪了"（1–5 条带日期的累计状态）。
- 体积超 40KB 时运行 `python scripts/archive_status.py` 自动保留最近 N 段（默认 10），其余原样移到 `文档/STATUS_归档_至<日期>.md` 并在头部留一行 `>` 引用。

格式（见 `assets/STATUS.md`）：
```markdown
## Handoff（YYYY-MM-DD）
- **谁做的**：工具【】/ 模型【】/ 家族【】；角色：执行方 / 复核方 / 主控
- **改了什么**：<新增/修改/删除的精确相对路径与核心结果，1–3 条>
- **怎么验证的**：<实际跑过的命令与结果原文摘要；没跑过的不要写已验证>
- **没做什么**：<明确未做项、范围外顺手发现的问题；没有写“无”>
- **不确定处**：<风险、UNKNOWN 或待确认项；没有写“无”>
```

**收工自检脚本**：`check_handoff.py` 查什么、怎么跑，见 `SKILL.md` 模式 A 第 8 步与脚本头部说明。

## 6. 命名约定 + 幂等性
- 输出文件命名带版本/日期/坐标系：`<output>_v1_20260615.tif`、`Fig_<topic>_<var>.png`，避免多 agent 产出同名覆盖。
- 长管线脚本**幂等**：有缓存（如已裁好的栅格）就跳过重算，重跑不从头开始。脚本开头：
  ```python
  import os, sys
  CACHE = r'F:\xxx_cache'
  os.makedirs(CACHE, exist_ok=True)
  FLAG = os.path.join(CACHE, 'done.flag')
  if os.path.exists(FLAG):
      print('skip (cached)'); sys.exit(0)
  # ... 干活 ...
  open(FLAG, 'w').close()
  ```
- 中间产物路径写常量置顶，方便核查与改盘。

## 7. 环境锁与环境坑清单
- **环境锁**：anaconda env 的包版本钉死，避免换机器重建时漂移：
  ```bash
  D:\software\...\condabin\conda.bat env export -n dlcm > environment.yml
  ```
  把 `environment.yml` 进项目（小文件）。`AGENTS.md` §7 放路径，`environment.yml` 放版本。
- **环境坑单一来源**：拷贝 `assets/环境坑.md` 到 `文档/环境坑.md`，记录本机软件、COM、云同步盘、DLL、编码等实测坑（现象 / 原因 / 解法 / 出处卡号）；`AGENTS.md` §7 和各任务卡只放链接，不在各卡重复抄写。

## 8. 数据快照 / 不可变输入
- 原始数据**只读**，所有 agent 在副本上动。
- 数据集目录放 `来源.txt`（见模板）+ 可选 `manifest.txt`（文件名 + sha256），校验没被改过。
- 判据：删掉所有中间产物，能从"原始 + 脚本"完整重跑出同样结果（可复现）。

## 9. 给 AI agent 委派任务的标准话术

每次委派新 agent 时，用统一格式开头——效果远好于自由发挥：

> 请先阅读 AGENTS.md（含 STATUS.md 了解当前状态）。
> 不要修改原始数据（<路径>）和已有核心代码（<路径>）。
> 红线（不可触碰）：<列不可修改的生产参数/路径/数字。例：生产方程参数不可改、最终头条数字不可覆盖>
> 本次任务只处理阶段 X。
> 如果发现疑点或新问题，记录到 <指定文档>，不要直接修正。
> 输出落在 <指定路径>。
> 本任务已知坑：[链接 `文档/环境坑.md` 对应条目 + 本卡特有风险点]
> 交付前必自查：[重开最终交付物核页数/文字/图片数 + 守恒/边界/格数/量级…，逐条用脚本过]

这个模板的核心价值：让新 agent 冷启动时**立即知道该读什么、不该碰什么、出问题往哪汇报**。其中"已知坑"和"必自查"两栏是**实战验证过的关键增量**——引导 agent 在报完成前自拦截常见错误类型，大幅降低缺陷率。对于影响论文结论或下游管线的关键任务，末尾追加「交付后安排独立复核」指示。

> **派发提示词随卡走（推荐）**：别让用户每次现填这段话术——**每张任务卡末尾内置填好的『📋 执行方派发提示词』和『📋 独立复核方派发提示词』块**（见 `assets/任务规划_模板.md`）。卡建好时就把目标/边界/输入输出/已知坑/闸门/收工填进去，用户要派活时直接复制那段贴给任何 agent（含跨工具、跨技能）即可，零现编。多树、迁移、克隆场景还必须先运行 `git rev-parse --show-toplevel`，与任务卡记录的仓库根完整绝对路径比对，不一致立即停下报告；该仓库路径身份与模型身份留痕是两个不同字段，不得混用。

## 10. 独立复核协议（Independent Review Protocol）

关键产物的独立复核**不是锦上添花，是链路可信的前置条件**：
- 主控或第三 agent（论文结论/头条数字类须不同模型家族）抽验关键数字：守恒（输入总和 ≈ 输出总和？）、边界（有无越界/未裁净？）、格数（行数/像元数符合预期？）、量级（单位是否差 10³？）、一致性（各文档中同一数字是否一致？）。
- 复核方不复用执行方脚本，自己写 `scripts/review_<task>.py` 或临时脚本独立重算，重开最终交付物核对。
- 先冷读成品（不读“主控在立项前看过什么”“🔒”节和执行方说明），再对照卡面；报告分 `## 会出错`（写清出错场景）和 `## 建议` 两节，末尾单独一行写 `PASS` 或 `NEEDS_FIX`（检查器 A012 提示）。只按“会出错”返工，最多 3 轮（详见 `assets/任务卡_README.md`）。
- 💡 短链路（1–2 个 agent、产物简单）可跳过独立复核（核心工作流第③步）；产出影响论文结论或下游管线的，**必须**走完 5 步。

## 11. 关键数字一致性核对清单（Shutdown Number Audit）

收工前，对一遍所有文件里的同一数字，跑核对脚本：
```bash
grep -n "MAOC" docs/*.md STATUS.md AGENTS.md  # 揪出所有出现过该数字的地方
```
- 页数、条数、图数、均值、合计、占比等计数和派生数一律由脚本算出，留存命令与结果，禁止心算。
- 同一数值在不同文件差 1% 以上即标记 bug。

## 12. 模型战绩表（`文档/模型战绩.csv`，派单参考）

长周期多卡项目可维护一张轻量的 `文档/模型战绩.csv`，按任务类型记录各模型的真实交付表现，派发新卡选模型时先翻表参考（借鉴 aicross TASK-69 思路，仅做事实汇总供人/主控参考，不做自动推荐引擎）：

```csv
卡号,任务类型,角色,工具,模型,家族,结果,复核会出错条数,备注
T8,建模,执行方,Claude Code,GLM-5.3,智谱,一次通过,0,R/Python 双实现一致
T10b,出图,执行方,Codex CLI,GPT-6,OpenAI,返修后通过,2,首轮漏指北针字号
T12c,写作,复核方,Claude Code,GLM-5.3,智谱,一次通过,4,独立重算抓出 4 处真错
```

字段约定：
- `任务类型`：`数据 / 建模 / 出图 / 写作 / PPT / 核查 / 复核` 等。
- `结果`：`一次通过 / 返修后通过 / 退回`。
- `复核会出错条数`：执行方填其产出被复核抓出的 `## 会出错` 条目数；复核方填其抓出并经主控采纳的真错数。

## 13. 卡头“任务契约”四行（一眼对齐边界）

任务复杂或跨工具频繁派发时，可在任务卡标题正下方、“进度回写”上方加一个四行的 `## 任务契约` 块，把原本散在“范围”行和“大白话：为什么要做”里的边界浓缩成四句：

```markdown
## 任务契约
- **目标**：【一句话写清本卡要交付的核心结果】
- **范围**：【输入、对象、工具或目录边界；核查类写“全部 X”】
- **不做**：【明确排除的事项、不碰的上游产物或红线】
- **验收**：【可运行验证的通过标准（脚本命令、计数或复算判据）】
```

出卡方写完这四行再展开下文；执行方开工、复核方第二阶段对照时一眼即可判断有没有做偏、漏项或越界。
